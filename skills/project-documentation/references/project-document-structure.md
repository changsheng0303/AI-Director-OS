# Project Document Structure

Use the smallest set of sections that fully describes the project.

## Core sections

1. **项目概览** — what the project is, current phase, owner if known, document version/date.
2. **目标与范围** — intended outcome, included work, explicit non-goals.
3. **背景与依据** — source material, user requirements, research or repository basis.
4. **流程或架构** — only when the project has multiple stages or components.
5. **当前状态** — completed, in progress, blocked, and not started. Do not mix plans with completed work.
6. **关键决策** — decision, rationale, impact, date/status.
7. **交付物** — files or artifacts, their status, and links/paths.
8. **评估与对比** — use for audits, options, benchmarks, or external-project reviews.
9. **风险与问题** — severity, evidence, impact, and mitigation.
10. **下一步** — concrete, ordered actions; include owners or prerequisites only when known.
11. **版本记录** — document version, date, change summary.
12. **来源** — repository, attachment, project file, or authoritative source.

## Information labels

- `已确认`: explicitly stated or verified.
- `已完成`: observable output exists and was checked.
- `进行中`: active work exists but is unfinished.
- `待决策`: a user or stakeholder choice remains.
- `建议`: analysis or recommendation, not project fact.
- `风险`: plausible issue with evidence or reasoning.

## Markdown principles

- Prefer prose for explanation and tables for true comparisons/status matrices.
- Link real files with meaningful labels.
- Keep one source of current status; avoid a second summary that can drift.
- Do not paste raw logs, full prompts, or every Schema field into the project record.

## Word principles

- Use the same content and section order as the approved Markdown unless layout demands a small presentation change.
- Use a quiet cover/title block, executive summary, restrained color, and full-width tables.
- Avoid decorative dashboards, dense metadata grids, tiny fonts, and table-first prose.
- Always render and inspect every page before delivery.
